## Regras de Negócio

- [x] **Curso não mapeado na importação:** resolvido em 2026-07-03 — o wireframe `docs/wireframes/03_importacao.html` mostra explicitamente "Criar curso automaticamente ao encontrar nome novo na planilha" como o comportamento padrão. Implementado dessa forma em `apps/api/src/modules/importacao/importacao.processor.ts`. **Ainda não é configurável de fato** (fica hardcoded até o módulo `configuracoes` existir no Sprint 5) — quando existir, expor como campo em `Configuracao` e ler o valor real em vez do padrão fixo.
- [ ] **CPF inválido ou duplicado com dados divergentes** (ex.: mesmo CPF, nomes diferentes entre importações): qual o critério de decisão — manter o nome mais recente, o mais antigo, ou gerar alerta para revisão manual?
- [x] **Cálculo de multa e juros:** resolvido em 2026-07-03 (decisão do usuário) — **Multa = 2% flat sobre o valor bruto da parcela** e **Juros = 0,033% ao dia de atraso** (contado do vencimento até a data de geração do relatório), ambos configuráveis via `Configuracao.multaPercentual`/`Configuracao.jurosDiarioPercentual` (padrão de fábrica lido de `MULTA_PERCENTUAL`/`JUROS_DIARIO_PERCENTUAL` no `.env` na primeira criação do singleton). O usuário também pediu um controle para a contagem de dias: `Configuracao.jurosContarDiaGeracao` (`true` = conta até o dia da geração inclusive; `false` = conta só até o dia anterior) — implementado em `apps/api/src/modules/relatorios/calculo-financeiro.ts`. Isso substitui a tentativa anterior de reverso-engenharia a partir dos documentos de exemplo (que batia a multa mas não o centavo de juros com 1% a.m.) — 0,033%/dia é o valor oficial informado pelo usuário.
- [x] **Regra de elegibilidade combinada:** resolvido em 2026-07-03 (decisão do usuário) — cada critério (parcelas mínimas vencidas / dias de atraso) só é aplicado quando preenchido (> 0); se apenas um estiver definido, só ele é exigido; se os dois estiverem definidos na mesma geração de relatório, ambos são exigidos juntos (E). Implementado em `apps/api/src/modules/relatorios/relatorios.service.ts`. Os valores podem vir de `Configuracao` (padrão) ou serem sobrescritos por filtro explícito na tela de geração (wireframe `04_relatorio_inadimplencia.html`).
- [ ] **Renegociação:** ao marcar uma parcela/matrícula como "Renegociado", o sistema deve gerar novas parcelas automaticamente ou isso fica fora do escopo do MVP (apenas mudança de status/situação)?
- [ ] **Sem tela de gestão de `SituacaoCobranca`/`Tag` (2026-07-03):** o CRUD existe na API (`/api/cobranca/situacoes`, `/api/cobranca/tags`), mas não há tela de administração — hoje só é possível cadastrar via API diretamente. Avaliar se entra no Sprint 5 (Configurações) ou se precisa de tela própria antes disso, já que sem isso o time não consegue cadastrar situações/tags pela interface.
- [ ] **Filtros de aluno/matrícula no relatório (PRD 23.4) não implementados:** a tela de geração de relatório (Sprint 4) só ganhou os filtros financeiros e de cobrança; filtros por CPF/nome/cidade/estado do aluno ou por curso/data/contrato da matrícula ficaram de fora — a prévia de elegíveis já parte de "quem tem parcela vencida" e esses filtros pareciam redundantes com as telas de Alunos/Matrículas. Confirmar se são realmente necessários aqui.
- [ ] **"Observação em lote" sem campo na UI:** o endpoint `POST /api/cobranca/lote` aceita um campo `observacao` para todas as matrículas selecionadas, mas a tela de relatório só expõe os selects de situação/TAG (como no wireframe `04_relatorio_inadimplencia.html`, que também não tem esse campo). Avaliar se vale adicionar.
